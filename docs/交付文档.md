## 一、系统概览

两个页面、一套数据、两条发布通道。

| 页面 | 路径 | 用途 | 数据来源 |
|---|---|---|---|
| **在途看板（总页面）** | `/`（`index.html`） | 全站首页「总览」+ 在途概览、周计划、逾期、产能、产线时效、准交率、交叉分析 | `data.json`（构建时内联进 HTML） |

两个页面共享品牌与视觉体系，但数据源不同：

- 看板读 `data.json`（金蝶采购订单全量）。
- 管理台读 `weekly.json`（金蝶采购申请单，申请单驱动）。
- **总览只在看板里**，管理台不再有总览页签。

```

   │  每日 09:15 / 14:30 / 17:45 自动导出

src/*.xlsx（4 张）
   │
   ├─ clean.py ──────────────► data.json

                                  │
                                  ▼
```

**关键约定**

- `run.py` 是唯一入口：`python run.py` = clean + build。
- `build.py` 会顺带调用待下单构建，所以日常只需跑 `run.py`。
- 任何对 `index.html` 的手工修改都会在下次 `build.py` 时丢失——**必须改 `index.template.html`**。

## 五、版本管理与回滚（重点）

### 5.1 三层留痕

| 层级 | 位置 | 能做什么 |
|---|---|---|
| 页面快照 | `versions/vX.Y.Z_DATE/` | 双击 `index.html` 看当时完整页面（含内联数据，零依赖） |
| 源码 | git commit + tag `vX.Y.Z` | `git checkout v2.0.0` 精确回到该版本源码 |
| 数据 | `src/` 历史 + 快照内联数据 | `git log -- src/` 追溯源表变化 |

### 5.2 新增一个版本

```bash
cd supply-dashboard
python archive_version.py --type minor \
  --title "一句话摘要" \
  --desc "具体改了什么" \
  --reason "为什么改" \
  --impact "影响哪些页面/口径/文件"
```

脚本会：抓取当前页面快照 → 复制 `console/` 与 `index.template.html` → 写 `delivery-note.md` →
更新 `versions/INDEX.md` 与记忆档案 → commit + push → 打 `vX.Y.Z` 标签。

`--type` 选 `major`（结构性）/ `minor`（功能）/ `patch`（小修）/ `before`（改前存档）。

### 5.3 回滚线上到某个版本

**方式 A：用快照文件覆盖（最快）**

```bash
cd supply-dashboard
cp -f versions/v1.6.2_2026-10-20/index.html            index.html
cp -f versions/v1.6.2_2026-10-20/console/index.html    console/index.html
# 再走一遍 4.2 的同步 + 发布
```

**方式 B：用 git 标签**

```bash
git checkout v1.6.2 -- index.html index.template.html console/index.html
python run.py          # 让数据回到最新（若只想回滚界面而保留数据）
```

**方式 C：整体回到旧版本**

```bash
git checkout v1.6.2
# 注意：会同时回滚数据处理逻辑，之后需要重新跑同步
```

> 回滚后务必核对：`data.json` 的 `meta.updated_at` 是否合理，待下单行数/件数是否与源表一致。

## 八、口径速查

| 指标 | 定义 |
|---|---|
| 在途（剩余收料） | Σ`remain`，可按交货月筛选 |
| 逾期 | `overdue_days > 0` 的剩余量 |
| 待下单 | 采购申请单「剩余数量 > 0」且单据未关闭/未作废 |
| 准交率（**准交率页**） | Σ(收料日期 ≤ 采购订单交货日期 的收料量) ÷ Σ收料总量（收料单口径，见 8.1） |
| 准交率（**交叉分析评分**） | 采购部工作台口径 `judge_std`，见 8.1 |
| 完成率 | 已收 ÷ 采购总量 |
| 负荷率 | 该月在途 ÷ 供应商月产能（月产能不跨月累加） |
| 排除项 | 物料编码含 `VYTK` 的一律不计 |

### 8.1 站内有两套准交率，不要混用

| 用在哪儿 | 数据来源 | 算法 | 11 月实测（整体） |
|---|---|---|---|
| 准交率页（OTD） | `src/otd_recv.xlsx` + `src/otd_po_full.xlsx` → `otd.py` | 收料日期 ≤ 采购订单交货日期 | **81.4%** |
| 交叉分析 · 供应商评分 | `k3_live.json` → `build_k3live.py` import skill 的 `judge_std` | 按 P0–P5 优先级算「标准时效」，实际时效对比标准时效 | **77.9%** |

两者对同一家供应商可能差很多（例：格莱尔 16.7% vs 22.6%，浩川 86.8% vs 72.2%），原因是**分母和判定基准都不同**：

- OTD 页：分母是「收料总量」，判定基准是采购订单上写的交货日期，VMI 调拨已剔除。
- 工作台口径：判定基准是按产线/时效标签/新品/皮革午餐包/佳俊高端/国际站等规则推出的「标准时效」，
  分母含 VMI 调拨，且 `build_k3live.py` 第 7 个参数 `is_leather_lunch` 硬编码为 `False`
  （皮革午餐包 P0 规则不触发，格莱尔会被低估）。**这是照搬工作台口径，不是本站的 bug，勿擅自"修"。**

要做的是"选一个当唯一口径"，而不是把两个数字对齐。目前交叉分析评分用工作台口径（与采购部工作台同源），
准交率页保留收料单口径（回答"这批货有没有按时到"）。任何一侧改口径，必须同步改本节。

### 8.2 供应商综合评分（交叉分析）

```
综合分 = 准交率×35% + 逾期控制×25% + 规模贡献×20% + 产能负荷×10% + 新品准交×10%
```

| 维度 | 算法 |
|---|---|
| 准交率 | 工作台 `rate`，直接取 |
| 逾期控制 | `逾期未交÷当月在途` min-max 反向归一化 × 准交修正系数(0.5+0.5×rate) |
| **规模贡献** | `在途订单数量` min-max 正向归一化 × `准交率/100` —— **乘法**：量大准交低不加分，量小准交满分也拿不到高分 |
| 产能负荷 | 负荷越低分越高（有余量能接单）；负荷率 = 当月在途 ÷ (月产能 × 当月剩余天数比) |
| 新品准交 | 工作台 `newRate`；无新品分母给中性 50 分，不惩罚 |

边界：在途为 0 不显示；无准交率不评分；矩阵页只统计**总在途 ≥ 6,000** 的供应商（指标卡同口径）。
脚本：`build_supplier_score.py`（`build.py` 每次构建自动调用）。规则细节见 `docs/供应商评估规则_2026-11-19.md`。

### 8.3 管理台的两个 script 块（改代码前必读）

`console/index.html` 由**两个独立的 `<script>` 块**组成：块0 = 主控制台（映射/匹配/汇总/核查），
块1 = 周计划 + 待下单 IIFE。**两块作用域互相看不见**，直接调用会抛 `ReferenceError`。

块0 末尾统一把跨块要用的函数挂到 `window.__core`：

```js
window.__core = { fmtYMD, renderStats, toast, refreshFoldSums };
```

块1 顶部再取别名：

```js
var _CORE = window.__core || {};
var fmtYMD = _CORE.fmtYMD;
```

**最坑的地方**：多数调用点外面包着 `try{...}catch(e){}`，抛错会被静默吞掉，
表现为「点了没反应」「图不动」，日志里什么都看不到。2026-11-19 的「趋势图筛选不刷新 + 点不开明细」
就是 `fmtYMD` 跨块引用被吞导致的。新增跨块调用时，**不要**用 `try{}catch(e){}` 兜底，
至少 `console.warn(String(e))` 打出来。

### 8.4 明细层的 SPU 列

趋势抽屉的 SKU 层、供应商详情 → SPU → SKU 层，都已锁定单一 SPU，
所以**不显示 SPU 列**（`wkDetailHtml(..., {hideSpu:true})`）。
SPU 只在「SPU 汇总层」出现，且用灰蓝胶囊标签；数量一律品牌蓝加粗（`.wk-qty-strong`）。
